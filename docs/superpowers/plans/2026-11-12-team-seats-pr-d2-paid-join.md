# Team seats, PR D2: Joining a Team From a Paid Plan Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an invited person with their own paid plan join a team, by ending that plan at Stripe first with the unused part credited to their Stripe customer balance, and end a paid plan that lands on a workspace nobody administers, all behind the switch that stays off in production.

**Architecture:** The plan is ended at Stripe before the join, outside every lock, and then the join that exists today runs. Under its locks `why_not_join` refuses to commit while the local mirror still shows a plan, and only Stripe's own replies, read back after the calls, write that mirror. The webhook ends a paid plan on a workspace nobody administers with the same helper, after its lock is released. Nothing new is stored: there is no model field, migration, `on_commit`, setting, URL or JSON code.

**Tech Stack:** Django 6.1.1, Django REST framework, django-oauth-toolkit, stripe-python 11.0.0 (API version 2025-03-31.basil), SQLite in tests, Postgres 16 in the rehearsal, Postgres in production.

**Spec:** `docs/superpowers/specs/2026-11-05-team-seats-design.md` (decision 3, at line 25, and section 9, question 4, at line 110). The PR D plan, `docs/superpowers/plans/2026-11-12-team-seats-pr-d-billing.md`, holds decision 12 (line 85), decision 13 and the list "Carried to D2, E and F" (line 424), which this plan takes up. ## Decisions this plan takes

The owner reviews these with the plan. Each gives its reason.

1. **Cancel first, then join, with nothing new stored.** A Stripe failure then leaves the person as they were before they pressed Join: an individual on their own plan, refused, with their keys working. Joining first would leave a member whose old plan keeps billing and who cannot reach it, because a member gets `administrator_only` from every billing call (`backend/drop_billing/account.py:647-649`, `720-722`, `932-934`). If wrong: the join-first design that was not chosen, with its table of owed endings, a lease worker and a sweep.
2. **The check under the join's locks is the only decider.** `why_not_join` gets one last code, `own_plan_ends`: an administered workspace whose mirror shows a plan (`plan != "free"` or a non-empty `stripe_subscription_id`) and that has a Stripe customer. `has_paid_plan` narrows to such a workspace with no Stripe customer, which is a plan Veilfile set by hand, and keeps its place. Every other refusal comes first, so a wrong person, an unverified address, an administrator of people, a suspended account, a hand-set plan and a full team never reach Stripe. The join commits only when the mirror it reads under the locks shows no plan. If wrong: a stored marker of the ending and a migration.
3. **What starts an ending, and what it ends.** Only `own_plan_ends` starts one, so a person whose mirror shows Free never touches Stripe at the join, as today. Once it starts, every subscription that Stripe lists in `LIVE_STATUSES` on that customer is ended by its own rule, and the result is applied once at the end. The one exception is a subscription whose `metadata.workspace_id` names another workspace. It is left alone, logged at ERROR and counted as `stuck`, because `stripe_customer_id` is neither unique (`backend/drop_core/models.py:38`) nor read-only in the admin (`backend/drop_core/admin.py:21`), Checkout always sets that key (`account.py:554`), and a cancel of another workspace's plan cannot be undone. A subscription without the key is ended. Anything live that is left could bill or revive, and one apply at the end avoids `_switch`'s pitfall, where a late failure rolls back an earlier true write. When the person administers more than one such workspace, the ending stops at the first whose ending is not done, so a refused join ends as little as possible. If wrong: a Stripe listing at the join of every person with a Stripe customer.
4. **The rule for each status:**

   | Status | First | Then |
   |---|---|---|
   | `active`, also with `cancel_at_period_end` | nothing | cancel with `prorate=True, invoice_now=True` |
   | `active` with `pending_update` | void the latest invoice | cancel with `prorate=True, invoice_now=True` |
   | `past_due`, `unpaid` | void the latest invoice | cancel with `prorate=False, invoice_now=False` |
   | `trialing`, `paused`, `incomplete` | nothing | cancel with `prorate=False, invoice_now=False` |

   Stripe advises voiding an unpaid invoice and not prorating unpaid time, and a pending switch is undone by voiding its invoice, as `_cancel_pending` does today. A failed void counts as a failure for that subscription, and no cancel is sent for it. A subscription with no latest invoice id is canceled without a void. A subscription schedule gets no special handling, so a cancel that a schedule blocks is `plan_not_ended` until staff act. The `active` row is what the owner saw in test mode on 2026-11-12: the subscription canceled at once, a negative draft invoice that Stripe finalized about an hour later, and the customer balance credited then, with no refund and no credit note. Every other row is unverified (question 6). If wrong: one row of `_how_to_end`.
5. **The calls.** The cancel is `stripe_mod.Subscription.cancel(sub_id, prorate=..., invoice_now=..., max_network_retries=0)`, with both flags always explicit and no `cancellation_details`. The SDK says that `invoice_now` defaults to true and the basil reference says false, so neither default is relied on. A DELETE carries no idempotency key, so a library retry of a cancel that took effect would meet a canceled subscription and get an answer nobody has seen. `max_network_retries` is a request option in stripe-python 11 (`venv/lib/python3.12/site-packages/stripe/_request_options.py`), so it reaches the library and not Stripe. The void is `_cancel_pending`'s inner call, `stripe_mod.Invoice.void_invoice(invoice_id)`, with the id read as `_cancel_pending` reads it (`account.py:863-864`), moved into `_latest_invoice_id(sub)` for both to use. `_cancel_pending` itself is not reused, because it returns a billing `Answer` and logs that the workspace stays on its plan. Every call goes through `_stripe_or_503()`. If wrong: one keyword on one call.
6. **Stripe's replies are read back.** After the voids and cancels, whether or not one raised, the customer's subscriptions are listed once more outside any lock. Each cancel reply replaces its id in that listing, as `_switch` does (`account.py:810-811`), and `_sync_from_subscriptions` applies it once. The ending counts as done only when that listing, with the replies in it, shows nothing in `LIVE_STATUSES`. A failed read-back writes nothing and counts as not done. When the first listing shows nothing live, no call is made and the first listing is applied. A missing customer at either listing goes through `_forget_missing_customer`, as everywhere else, and counts as done. Reading back is Stripe's advice for an unknown outcome: a cancel whose answer was lost lets the join go on in the same request, and a checkout that completed during the calls is seen instead of being overwritten with Free from an older listing. A listing can also be older than the row by the time it is applied, when a webhook writes a new subscription between the listing and the apply. So each apply of an ending passes the ids it knows, which are the ids of its listing and the id that the row named when the request read it, and `_sync_from_subscriptions` writes nothing when the row it locks names a subscription that is not among them. The listing asks for every status (`account.py:265-267`), so only a row that a webhook wrote after the listing can name one. A row that still names an id that Stripe does not list, set by hand or left by a staff edit of the customer id, is applied as it is today. The ending then counts as not done, and the check under the join's locks meets the plan that the webhook wrote. The ending reports three facts, Task 2's `Ending`. `done` is the condition above, and it also needs the apply to have written. `cut` is true when a cancel it sent took effect, by its reply or by the read-back. `stuck` is true when a subscription it tried to end is still live in the read-back, when it left a subscription that names another workspace (decision 3), or when a listing failed. If wrong: one listing less, and a lost answer becomes `plan_not_ended` until the webhook lands.
7. **The Join form carries consent.** It holds `<input type="hidden" name="own_plan" value="ends">` only when the page shows the own-plan sentences. On an accept, when the unlocked check answers `own_plan_ends` and the POST lacks `own_plan=ends`, no Stripe call is made. The page is shown as a GET would show it now, with the offer and Join, at 400, which is the status the view already gives an accept that did not join. A cancel cannot be undone, and a plan bought between the GET and the POST was never mentioned on the page the person read. For the same reason, the offer is shown again at 400 when the check under the locks answers `own_plan_ends` after this request made no attempt to end a plan, or after an attempt that is not `stuck` (decision 8). If wrong: one hidden input and one check.
8. **An ending that did not complete is a refusal while the mirror still shows a plan, `plan_not_ended`.** When this request tried to end the plan, the ending is `stuck`, and the check under the locks still sees a plan, `accept_invitation` raises `JoinRefused("plan_not_ended")`. When the only live subscription left is one the first listing did not show, such as a Checkout completed during the calls, the ending is not `stuck`, and the person meets the offer again at 400, because they never agreed to end that plan. When what is left grants nothing (`unpaid`, `paused` or `incomplete`), the mirror is Free and the join commits. The ERROR stays, and the webhook ends that subscription if it revives. The page gives `plan_not_ended` its own branch, because the template's `{% else %}` branch shows Join for any code it does not name (`invitation.html:34-48`). Every other refusal from the join keeps its code. A person who meets it opens the link again, and the second press finds the plan ended and joins, or meets the same refusal until staff act on the ERROR line. If wrong: one code and one template branch.
9. **A refusal after the plan ended says so.** `JoinRefused` gains `plan_ended`, true when a cancel this request sent took effect (`cut`). Whichever page the refusal renders, the invitation page at 400 or the not-valid page at 404, then carries the Words sentence after its first paragraph. `plan_not_ended` never carries it, because its own sentence says that Stripe did not confirm the ending. A double press that the other request already joined still redirects to Overview with nothing added, because that person is on the team. This tells the person in the design's worst state, a plan ended and no team, what happened. If wrong: one attribute and one sentence.
10. **The webhook ends a paid plan nobody administers, only with the switch on.** With the switch on, `_sync_workspace` no longer reports under its lock. After it returns, `_handle_event` calls `end_unadministered`, which ends the plan when the workspace's plan is not Free and `_open_administrator` finds no row. It logs one WARNING with ids when a cancel it sent took effect, and nothing when it finds the plan already ended. When the ending is not done, it logs an ERROR and raises `PlanNotEnded`, which the webhook answers with 500 and no `ProcessedStripeEvent` row, so Stripe retries. A failed ending whose read-back is applied also logs today's "reconcile it by hand" ERROR, because that apply goes through `_sync_from_subscriptions`, which reports as it does today. With the switch off, `_sync_workspace` logs today's ERROR for the same events, and nothing is canceled. Both new public helpers also return before any query or Stripe call while the switch is off. The status refresh and `sync_stripe_billing --apply` keep the ERROR with the switch on or off. An automatic cancel cannot be undone, and nothing can make a workspace nobody administers while the switch is off, so a hit there is a data fault that staff should see first. The administrator read is a plain read after the commit, so no Stripe call runs under a lock, and it costs the one query that today's `.exists()` costs, only for a paid plan. If wrong: one settings check.
11. **A read-only check before F.** `sync_stripe_billing --list-unadministered` prints each workspace that has a paid plan or a subscription id and no open administrator row, with ids only, and then a count. It returns before the key check (`sync_stripe_billing.py:83-85`), so it runs without a key and contacts nothing, and it refuses `--apply`, `--reset-unbilled`, `--list-orphans` and `--allow-test-key` beside it. One ERROR per workspace names the subscription that the listing read after the calls still shows, so staff act only on an ending that is stuck. If wrong: the levels of the log lines.

## Review Focus

1. **A person who canceled in the portal, so `cancel_at_period_end` is set, then joins.** The plan ends now, and the cancel asks Stripe to prorate it. ## Changed during the build

Before Task 1, a scan of the whole plan found six places where its text disagreed with itself. The plan above carries the rulings.

- The guard on `_sync_from_subscriptions` takes `known_ids`, the ids of the listing together with the id that the row named when the request read it. With the listing's ids alone, a row that named an id Stripe does not list would never have been applied, and that person would have met the offer on every press.
- Five sentences were made exact. The byte rule for the templates leaves out `has_paid_plan`. The "reconcile it by hand" ERROR comes only from a read-back that is applied. A subscription of another workspace stops a join only while it grants a plan. The rehearsal's checkout race expects one "keep one and refund the others" ERROR. The rehearsal's delayed cancel takes effect before it waits.
- After Tasks 2 and 3, their reviews left three small findings, and a short task (3b) fixed them. An ending whose listing was not applied because the workspace had moved to another customer now counts as not done, as decision 6 says, and it logs the same INFO line. A workspace with no Stripe customer makes no listing and counts as done, and a test now pins that. The new test module no longer imports a name that it does not use.
